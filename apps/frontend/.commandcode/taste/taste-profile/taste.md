# Taste Profile
- Strongly values UI consistency across the app — repeatedly asks to make sections "compatible with" the design of reference sections (e.g., Endpoints ↔ Incidents, Users ↔ SignIn, TopBar ↔ Sidebar ↔ SignIn). When implementing a new section, treat visual consistency with existing established sections as a first-class requirement. When asked to mirror a reference component, match it at every level (structure, styling, AND icon library/family), not just the visual skeleton. Confidence: 0.95
- Treats the sign-in page as a design reference/anchor — multiple redesign requests explicitly anchor new work to "the design of signin page". Sign-in page aesthetics (animations, colors, gradients, rounded corners) are the canonical style. Confidence: 0.9
- Prefers gradient buttons for primary actions (e.g., gradient submit button, gradient tab buttons matching sidebar icon buttons). Gradients should be defined once in a shared, app-wide location, not recreated per-component. Confidence: 0.9
- Prefers status/severity/sourceType rendered as chips rather than plain text or colored cells in lists and detail modals. Confidence: 0.85
- Wants subtle shadows and borders tuned per theme — e.g., darker shadow on active tab buttons in light mode, slightly darker table border in light mode. The user notices and asks for tweaks on small visual details (font weight, padding, border-radius, icon size). Confidence: 0.85
- Prefers thin/slim chrome — repeatedly asks to make the sidebar and topbar thinner ("a very little thinner"). Default density should be compact. Confidence: 0.85
- Prefers collapsible sidebar with icon-only collapsed state. Active item styling differs between open and closed states (closed = primary-color background, no left bar). Confidence: 0.85
- Persists sidebar collapse state in cookie/localStorage (not React context) so it survives reloads without flicker; uses skeleton loading and entry animations while items mount. Confidence: 0.85
- Prefers icons over text in compact UI affordances (e.g., create button as IconButton, topbar profile as icon, show-all toggle as animated icon). Confidence: 0.8
- Prefers filled icons for active/selected states (filter icon, profile icon) and uses animations on icon transitions. Confidence: 0.8
- Wants clear visual feedback on copy/clipboard actions: swap icon to checkmark, change color to success green, update tooltip/label text to "Copied!", and auto-revert after ~2 seconds with a smooth CSS transition. Confidence: 0.9
- Likes dividers to separate logical sections inside popovers/modals rather than relying on whitespace alone. Confidence: 0.8
- Prefers small border-radius on chrome elements (topbar, buttons) — not too curvy. Default is "a little rounded", not pill-shaped. Confidence: 0.8
- Prefers reducing margins/padding iteratively — gives fine-grained instructions like "a very little smaller", "make the edges more rounded", "decrease padding". Expect tuning conversations rather than one-shot designs. Confidence: 0.9
- Wants custom UI for enum-like fields (status, sourceType, triggerState) to use chips rather than raw Selects when displayed read-only, but uses TextField over Select in form layouts where space is tight. Confidence: 0.7
- Prefers feature-based folder structure for new features (e.g., `src/features/Incidents/`, `src/features/Runbooks/`). When asked to add a feature, organize by feature folder not by type. Each feature folder MUST include ALL related files — components, API helpers (`*.api.ts`), type definitions (`*.type.ts`), and utilities (`*.utils.ts`) — not just components. Use the Incidents feature folder as the canonical template for structure. Confidence: 0.95
- Prefers fine-grained feature separation — even closely related domain concepts (e.g., Endpoint vs EndpointFlow) should each get their own feature folder rather than being grouped under one umbrella. If two resources have distinct types, APIs, and modals, they are separate features. Confidence: 0.85
- Prefers feature-based folders over domain-specific subfolders within `src/components/` — if a component is tied to a feature (e.g., EndpointTypeChip), it belongs in `src/features/{Feature}/components/`, not in `src/components/Endpoint/`. Keeps `src/components/` for truly shared/generic primitives only. Confidence: 0.9
- Wants reusable UI primitives in shared locations (`src/components/`), not inside feature folders. Example: GradientSubmitButton moved out of `users/` into `components/` because "it may use in other page". When something is generally useful, move it to shared. Confidence: 0.9
- Prefers shared utilities/hooks/API helpers split out of individual page files so they can be reused — but they should live inside the feature folder (e.g., `src/features/{Feature}/`), not scattered across `src/utils/` or `src/api/`. Confidence: 0.85
- Prefers API helpers follow a consistent try/catch + typed AxiosError pattern returning `ServerResponse<T> | undefined`, so callers handle errors uniformly. Confidence: 0.85
- Wants API response shape to include a `status` field on create/update/delete (not just data) so the UI can react to success/failure consistently across resources. Confidence: 0.85
- Prefers enum-like fields (status, severity, sourceType, triggerState) to use string literal unions that match backend values exactly. Avoids index-signature parameter types — use mapped object types instead. Confidence: 0.8
- Wants tab/route state persisted via URL query params for pages with tabs (e.g., alert rule detail) so reload doesn't reset selection. Confidence: 0.8
- Prefers joining related pages into a single unified workspace rather than maintaining parallel pages (e.g., merging Incident + IncidentPolicy into one workspace with tabs). Confidence: 0.8
- For workspace tables with tab/segment switching, prefers the switch placed inside the table toolbar (via `renderToolbar`) replacing the table title — switch on the left, search/create actions on the right. Each workspace page should have a dedicated `{Feature}Toolbar` component following the `IncidentWorkspaceToolbar` pattern. Confidence: 0.9
- Wants unused files/routes removed after refactors (e.g., check if old `incident-policy/page.tsx` is still referenced, then delete). Confidence: 0.8
- Prefers details shown in modals rather than dedicated detail pages for list-driven resources (e.g., incident details in modal, not new page). Confidence: 0.75
- Watches for stale backend assumptions in the frontend — proactively asks to remove fields the backend no longer exposes (e.g., `serviceIds` in runbook). Confidence: 0.8
- Uses a plan-and-todo workflow: writes a plan, creates to-dos, then asks the agent to "Implement the plan as specified", "Do NOT edit the plan file itself", and "Don't stop until you have completed all the to-dos". When using this workflow, follow the plan, mark to-dos in_progress as you go, and complete them sequentially without re-creating them. Confidence: 0.95
- Often sends short follow-up commands like "1", "2", or short titles that re-confirm or pick from a multi-option plan the agent presented. Expect terse confirmations as selection mechanism. Confidence: 0.85
- Provides explicit, prescriptive change descriptions rather than open-ended goals (e.g., "make the buttons a very little smaller", "place severity and status in Details sections"). Honor the exact phrasing when possible. Confidence: 0.9
- Uses iterative refinement — same component gets many successive tweaks. Treat the first design as a starting point and expect multiple follow-up rounds of "a little smaller/bigger/darker". Confidence: 0.9
- Tags files with `@path/to/file.tsx` to anchor changes to specific files. Always respect the exact file path provided. Confidence: 0.9
- References markdown instruction/spec files in `src/instructions/` (e.g., `incident.md`, `incident-policy.md`) as authoritative domain specs. Read them before implementing features. Confidence: 0.85
- After the agent finishes, the user (or system) issues a "Perform any necessary follow-up actions in response to the subagent completion above" prompt. Use this as the trigger to review subagent work and decide whether more changes are needed; if not, acknowledge briefly. Confidence: 0.8
- Mentions when they've made manual changes ("I've just done some changes in @src/components/Wrapper/ just keep them") — respect and preserve those manual edits. Confidence: 0.85
- Uses Next.js (App Router, with `[locale]` segment) + MUI + custom theme with light/dark palette. Migrates to latest Next.js as it comes out. Confidence: 0.85
- Standard icon library for the project is `react-icons/ai` (Ant Design outline icons). When adding icons to a component meant to match existing chrome/tabs, use `react-icons/ai` icons — don't reach for other families (e.g., `react-icons/pi`/phosphor) just because they semantically fit. Codebase-wide icon consistency is required, not icon-theme variety. Confidence: 0.9
- Uses MUI Button `loading` prop instead of `CircularProgress` inside buttons. Confidence: 0.85
- Uses framer-motion (motion.div with initial/animate) for entry/exit animations on sign-in and chrome elements. Confidence: 0.8
- Prefers `text-wrap: nowrap` on sidebar item labels so they don't wrap when collapsed. Confidence: 0.75
- For custom SVG icons imported from `react-icons`, when one icon visually appears smaller than others at the same `fontSize`, scale it up explicitly via an `iconScale` constant. Preserve user-tweaked icon scales across edits. Confidence: 0.8
- For popovers (TopBarProfile, zone selector, search), wants matching background color and slightly more border-radius. Confidence: 0.75
- Treats runbooks, postmortems, documents as related siblings of incidents and prefers them handled together in planning. Confidence: 0.7
- Prefers readonly access to be visually distinguished in tables — restricted columns render "-" (notify, action), action buttons hidden, ownerName hidden, only certain tabs visible. Confidence: 0.85
- For form tip text under fields, prefers moving the content into the field label (in parentheses) rather than keeping a separate tip line. Confidence: 0.75
- Uses an "advanced behavior" pattern on alert rules with: dependency/filters (key-value), triggerState, and optional startsAt/endsAt date range. Validates that at least one condition is required. Confidence: 0.7
- When assigning colors to third-party integrations (e.g., Mattermost, Slack, Jira), prefers using the official brand color from the provider's own website/logo rather than arbitrary hex values. Confidence: 0.9
- Actively monitors dark mode readability — will flag and request changes when foreground colors (text, icons, chips) lack sufficient contrast in dark mode. Contrast compliance is a first-class concern, not an afterthought. Confidence: 0.85
- Expects root-cause fixes over layered workarounds — when a fix doesn't work after a first attempt, expects the agent to investigate library internals (e.g., reading source in `node_modules`) to find the actual cause rather than adding more surface-level patches. "Find a way to solve this" means dig deeper, not pile on more mitigations. Confidence: 0.9
- Requires the agent to actually test/verify changes after making them — will reprimand if the agent only edits code without confirming the fix works in a running instance (e.g., curl SSR output, browser testing, or running typechecks/tests). "Don't just change some code only" means proof is expected, not assumptions. For visual/theme bugs, SSR HTML or cookie presence alone is explicitly rejected as proof — requires real-browser reload observation on an authenticated page. Confidence: 0.95
- Prefers official library-provided solutions over custom hand-rolled implementations for well-known framework problems. When the user points to official documentation (e.g., MUI's dark-mode flicker page), the assistant should read and follow that doc instead of inventing custom workarounds. Confidence: 0.9
- Will share official documentation URLs to guide the assistant toward the correct solution when troubleshooting framework-specific issues. Always fetch and follow the linked doc. Confidence: 0.9
- Zero tolerance for flash-of-wrong-theme (FOUC) on page load — will report even a brief white flash before dark components render and will re-report if the first fix attempt doesn't fully eliminate it. Expects a defense-in-depth approach with all four layers: (1) CSS class-based rules in `globals.css` (`html.dark` / `html.light` with `background-color` and `color-scheme`) — parsed and applied before any JS executes or first paint occurs, (2) inline `style` attributes directly on `<html>` and `<body>` elements (backgroundColor, colorScheme, color) applied synchronously during DOM construction, (3) MUI's official `InitColorSchemeScript` (placed inside `<body>` before providers) that reads from `localStorage` and sets the correct class on `<html>` before React hydrates — the storageManager must use `localStorage` (not cookies) for this to work, with cookies synced separately for server-side reads, and (4) passing resolved theme from server-side cookies to MUI ThemeProvider `defaultMode` so Emotion generates correct CSS variables during SSR. Also requires `suppressHydrationWarning` on `<html>` and `<body>` to prevent React from briefly stripping and re-applying attributes during hydration. Confidence: 0.95
- For inline chip/tag lists that can vary in length (e.g., flow steps), prefers truncating to a fixed visible count (e.g., 3) with a "+N" overflow indicator rather than rendering all items. This keeps table rows compact and predictable. Confidence: 0.85
- When a modal or container's content overflows, prefers a clean scrollable list layout (with proper `maxHeight`, `overflowY: auto`, and dashed dividers) over cramped compact alternatives (horizontal chips, stat-heavy views) that sacrifice readability to avoid scrolling. Content must not overflow invisibly out of the viewport, but a well-spaced scrollable list is strongly preferred over dense layouts that try to fit everything on one screen. Confidence: 0.9
- Numeric input fields should default to empty, not 0 — pre-filling with 0 forces the user to delete it before typing their actual value. Minimizes friction in form inputs. Confidence: 0.9
- Prefers page-level backgrounds to be transparent, inheriting the app shell's background rather than applying their own `getAppBackgroundSx` wrapper. Keeps individual pages lightweight and consistent with the overall chrome. Confidence: 0.8
- Prefers a clear action-button hierarchy: only the most frequently used actions (e.g., test, silence) appear as top-level icon buttons; secondary or utility actions (e.g., copy curl, pin) belong inside the "more actions" popover (three-dots menu). Avoids crowding the action bar with infrequently used buttons. Confidence: 0.85
- React Query's `isLoading`/`isPending`/`isFetching` should be coerced to boolean with `!!` before passing to HTML boolean attributes (e.g., `disabled={!!isLoading}`) to prevent SSR hydration mismatches — these values can be `null` on the server but `true`/`false` on the client. Confidence: 0.9
- MUI dark mode: never use `theme.palette.mode === 'dark'` or `palette.mode` in style computations — this causes SSR/client mismatch because the server always renders `mode: "light"`. Instead, use `theme.applyStyles("dark", {...})` for theme-level overrides (e.g., in `styleOverrides`) or pre-compute via `useCurrentTheme()` hook for component-level usage. Confidence: 0.9
- Requires explicit approval before any git commit — do not commit automatically after edits; wait until explicitly asked to commit. Confidence: 0.85
- Prefers read-only detail views to resolve ID references to human-readable names via server-fetched lookup lists (e.g., endpoint/user/team/data-source names) rather than displaying raw ID strings. Confidence: 0.8
- Prefers missing/unknown status values to display as an explicit "Unknown" chip (styled like other statuses) rather than a "-" placeholder. Confidence: 0.75
- Prefers commit messages with no AI self-attribution — never include co-authored-by, generated-by, or other assistant/tool references in commits. Confidence: 0.95
- Prefers table columns that only open a row-details view to be labeled descriptively ("More Details" / "More Info") rather than generic "Action" / "Actions". Confidence: 0.85
- Prefers embedded JSON viewers to render with a transparent background (overriding the library theme variable such as --w-rjv-background-color) so they blend with the surrounding container in both light and dark modes. Confidence: 0.8
- For rows of adjacent action icon buttons, requires each button to have a visually distinct hue with sufficient light-mode contrast (not close shades of the same family), each with tooltip + aria-label. Confidence: 0.75
